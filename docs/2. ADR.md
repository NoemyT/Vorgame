# ADR-001: Arquitetura do MVP do Vorgame

**Status:** Aceito

## Contexto

O Vorgame é uma rede social de avaliação de jogos. O MVP cobre: criar conta, login, pesquisar jogos, visualizar detalhes, avaliar jogos (nota de 0 a 10, uma por usuário por jogo, média recalculada a cada avaliação) e publicar reviews. Os atributos de qualidade mais críticos são segurança, desempenho, escalabilidade e consistência de dados. A equipe é pequena e o prazo é curto. Funcionalidades sociais (comentários, notificações, recomendações) virão depois do núcleo.

O protótipo desta entrega é um recorte desse MVP: inclui HU01–HU05, com publicação e exibição de reviews adiadas junto com HU06. O catálogo será local, carregado inicialmente no MySQL por Prisma, sem integração externa ou interface administrativa nesta entrega. O escopo e o aceite estão registrados nas [histórias de usuário](1.%20Hist%C3%B3rias%20de%20Usu%C3%A1rio%20%28Alta%29.md).

## Decisão

Adotar a Proposta A: monólito modular em camadas (apresentação → aplicação/domínio → persistência), com API REST e um banco MySQL único, usando InnoDB e acesso por Prisma. O código será organizado em módulos com fronteiras claras (Usuários/Autenticação, Catálogo de Jogos, Avaliações, Reviews), de modo que cada um possa ser extraído como serviço no futuro. O módulo de Reviews permanece previsto na arquitetura e será implementado após o protótipo desta entrega.

## Alternativas descartadas

- **Proposta B (serviços + cache):** descartada para o MVP. Exige dois serviços, comunicação em rede, bancos separados e mais infraestrutura. Sem transação única entre bancos, a regra de uma avaliação por usuário com média atualizada ficaria mais frágil. Seus benefícios (escala independente, cache) respondem a uma carga que o MVP ainda não tem.
- **Monólito sem modularização:** descartado por favorecer o acoplamento e dificultar a entrada das funcionalidades pós-MVP.

## Consequências

### Ganhos

- Consistência garantida por transações ACID na regra de avaliação e no cálculo da média (HU05).
- Desenvolvimento e deploy simples, com entrega mais rápida do MVP.
- Menor custo operacional, adequado a equipe pequena e prazo curto.
- Segurança centralizada (senha, sessão, autenticação) em um único ponto.
- A modularização preserva um caminho de evolução para serviços.

### Custos aceitos

- Escalabilidade horizontal limitada: se a carga crescer, será preciso escalar o monólito inteiro.
- Ponto único de falha, o que reduz a disponibilidade em comparação a uma arquitetura distribuída (mitigável com réplicas e backups).
- Risco de acoplamento entre módulos ao longo do tempo, exigindo disciplina de modularização.
- Desempenho de busca e ranking sem cache no início; se necessário, um cache pode ser adicionado depois sem mudar o estilo da arquitetura.

# ADR-002: Stack de implementação do Vorgame

**Status:** Aceito

## Contexto

O ADR-001 define a arquitetura, mas não especifica as ferramentas de implementação. A equipe precisa de uma escolha concreta para desenvolver frontend e backend com apoio de IA e manter os dois alinhados.

## Decisão

- **Backend:** Node.js com TypeScript e NestJS, usando o adaptador Express. A validação de entradas usará DTOs, `ValidationPipe`, `class-validator` e `class-transformer`; a documentação OpenAPI usará `@nestjs/swagger`.
- **Persistência:** MySQL com tabelas InnoDB, Prisma ORM, Prisma Client e migrações com Prisma Migrate. O Prisma será integrado ao NestJS por um provider da camada de persistência. O banco é hospedado no TiDB Cloud (plano Starter, compatível com MySQL), em substituição ao Neon sugerido no enunciado, conforme combinado com o professor, já que o Neon oferece apenas PostgreSQL.
- **Frontend:** React com TypeScript, Vite, React Router, CSS e `fetch` para consumir a API REST em JSON.
- **Ambiente:** Node.js LTS em uma versão compatível com NestJS, Prisma e Vite, com npm nos dois projetos.
- **Testes:** Vitest e Supertest no backend; Vitest e React Testing Library no frontend.
- **Hospedagem:** backend no Render e frontend na Vercel, ambos nos planos gratuitos; o banco e o backend ficam na região leste dos EUA para reduzir a latência entre eles.

A stack segue a escolha de Node.js, NestJS, React, MySQL e Prisma definida para o projeto. NestJS fornece a organização em módulos e injeção de dependências; React e TypeScript permitem organizar as telas e explicitar os dados consumidos. Prisma fornece acesso tipado e migrações para o MySQL. O uso de InnoDB preserva as restrições relacionais e as transações necessárias às avaliações.

As versões exatas das dependências serão fixadas em manifestos e arquivos de lock na implementação. Esta decisão escolhe a stack; o contrato dos endpoints será documentado separadamente.

## Alternativas consideradas

- **Express diretamente:** oferece uma base menor, mas exigiria definir manualmente a organização de módulos e a injeção de dependências. O NestJS foi escolhido para padronizar essa estrutura.
- **TypeORM:** oferece persistência no ecossistema NestJS; a escolha do projeto é Prisma para centralizar o esquema, as migrações e a geração do cliente tipado.
- **Frontend sem framework:** atenderia às primeiras telas, mas exigiria organizar manualmente navegação, estado e atualização da interface conforme o sistema crescer.

## Consequências

- A arquitetura continua sendo um monólito modular com um banco relacional único.
- A equipe usará TypeScript no backend e no frontend, com Node.js para executar a API e as ferramentas de desenvolvimento.
- As restrições de unicidade e as transações deverão ser implementadas no MySQL via Prisma; tipos TypeScript e validação de DTOs não substituem a integridade do banco.
- A documentação gerada por `@nestjs/swagger` deverá ser conferida com o contrato aprovado; sua geração automática não substitui a definição dos endpoints antes da implementação.
- A configuração de dependências, execução e testes será acrescentada quando houver código executável.

Detalhes de cada parte estão nos READMEs de [backend](../backend/README.md) e [frontend](../frontend/README.md).
